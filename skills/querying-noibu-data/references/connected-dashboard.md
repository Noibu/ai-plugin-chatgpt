# Save as Live Site: private persistent report

Use this workflow for every analytics **Save as Live Site** action and equivalent natural-language Save as Live Site requests. "Live Site" means a published, reopenable Site; it does not mean continuously live Noibu data. The default mirrors saving an in-chat dashboard into a private Site with durable snapshot history. No visitor Noibu connection, spreadsheet, recurring task, or repository connection is required merely to save the current report.

Read the available Sites skill and its storage/identity guidance. This package supplies reusable report/persistence helpers, not an already-published Site. Keep the Site action independent from GitHub storefront-source investigation: Sites' own managed source repository is not a reason to prompt for merchant GitHub access.

Treat the button as the direct request: **Build a private interactive Site containing this dashboard that was just generated. Save the data between visits. Offer to refresh the dashboard once weekly with fresh data.** Offer the weekly option during setup, confirm its day/time/timezone and notification intent before scheduling, and let the user decline. Do not wait for scheduling choices to publish the current report. A selected save action is not approval to create a recurring task without those confirmed details.

Run [the Site permission preflight](site-permissions.md) before registration/build and before starting any publishing helper. Prefer supported native scoped approvals; otherwise explain the current-chat permission selector and optional non-managed Custom configuration. Never silently edit settings or automate the security selector. A prior successful Site does not prove this chat's permissions, and a previous denial does not prove the newly configured chat remains blocked.

## Complete the selected save

1. Recover the actual report and its domain, workflow, windows, currency, findings and limitations. Preserve the screenshot-inspired composition. Reuse its measured evidence instead of silently rerunning analysis or inventing a spreadsheet. A missing report requires a focused request for that evidence, not fabricated numbers.
2. Discover native Sites access. Resolve a matching Site using workflow + domain UUID/name and existing conversation/project identity; preserve its project ID, source and audience. Inspect uncertain registration/save/deployment outcomes before retrying. New Sites stay owner-private. Updating an existing shared Site needs the applicable supported audience/approval checks; do not broaden or narrow access silently.
3. Use a dynamic Sites starter with D1 for durable structured snapshots. Persist a nonsecret `noibu-dashboard-config.json`: workflow, domain identity, window/comparison rules, selected blocks, `dataMode: "persistent-snapshot"`, and any later approved refresh-source configuration. Create migration-owned tables through the starter's schema/migration workflow, not at request time. Source must contain only schema, layout, queries and a data loader—not baked-in customer report data. Seed the actual report into D1 via the supported private data-write path after the schema is provisioned. If safe seeding is unavailable, report that exact blocker rather than embedding customer data in tracked source.
4. Reuse the packaged [snapshot store](../assets/sites/snapshot-store.mjs). Its schema SQL is for a migration; its functions use D1 prepared statements, explicit trusted server-side authorization, workflow/domain scoping, content-hash deduplication, and readback. Author the server adapter using the current Sites identity/storage helpers. A false/missing authorization result must reject reads and writes. For an owner-private service writer, follow the platform's supported private-Site access boundary; do not invent a public unauthenticated update endpoint or put service tokens in source, report JSON, browser code or task prompts. Keep snapshot content outside source archives/plugin ZIPs.
5. Before saving, verify totals/rates against the original evidence: distinct sessions versus events, compatible cohort denominators, express-checkout skips, completed-order revenue/currency, and any additive breakdowns. Unknown is not zero; do not require unrelated segment rows or top-N tables to reconcile to population totals. Record the checks that actually passed and material limitations. Failed checks prevent promotion to the current snapshot; retain the last verified data. The helper validates the recorded check contract, not the truth of analytics—perform the checks before passing it evidence.
6. Implement server-rendered latest snapshot and history reads from D1, preserving values between independent requests/visits. Render provider text safely. Display data window, captured time, verification state, and **Saved snapshot — updates only when refreshed**. A Reload saved data control may reread D1; it must not claim to query Noibu. For hosted report controls, use copyable requests back to ChatGPT where no real native bridge exists. Do not embed the in-chat action controller in a Site or imply its buttons execute there.
7. Follow the current Sites checks, build, secure source synchronization, version save and private deployment workflow. Complete safe available work in the active turn; registration or a build is not publication. Await setup before dependent builds, repair concrete errors before retrying, and stop on a policy denial or uncertain still-running upload. Do not bypass restrictions with other credential transport, alternate network routes, duplicate helpers or security-setting changes.
8. After publication, seed/read back the verified snapshot using the supported private data path and check a fresh hosted read. Return only the successful deployment's literal URL. Distinguish **published, persistence verification pending** from **published and persistent**. A missing browser preview is a verification limit, not permission to claim it rendered. A failed save/read leaves the old snapshot visible with an honest stale/error state. On a blocker, report the exact failed phase/error, preserved artifacts, actual job state and next required action; no guessed URL or background-work promise.

Use the [progress checker](../scripts/dashboard_progress.py) with `mode: "persistent-snapshot"`. Record Sites access in `eligibility`; Noibu plugin-in-Sites eligibility is **not** a gate for this mode. Track dependencies → source/schema → checks/build → saved version → deployment → verification/seed → independent D1 readback → hosted read. A deployed URL does not prove persistence; a saved snapshot does not prove an unattended updater.

## Offer weekly updates during Site setup; schedule only after confirmation

For requested email/messaging notifications, use [provider-agnostic delivery discovery](scheduling-delivery.md) to resolve the actual connected sender/provider and destination and check unattended send capability. Keep this Site's linked schedule and protected update/readback path below; do not create a second standalone task just for delivery or require a provider-specific recurring scheduler. Delivery success and Site update success are distinct results.

Read current Sites recurring-update guidance before adding a writer or linked task. During setup explain the weekly refresh option; after resolving the Site and checking linked automations, ask “Would you like fresh Noibu data weekly? Which day, time and timezone, and what movements should notify you?” Reuse already confirmed settings instead of asking again; retain any different cadence the user requested. Preserve exact requested cadence/time/timezone; 8 AM must not become 9 AM. Ask when the timezone or significant-change definition is materially unclear. No schedule is created by Save as Live Site alone, and declining or deferring it must not block saving/publishing the report.

Default a requested Noibu dashboard refresh to the original Noibu queries with fresh relative windows. A spreadsheet is a source only when the user actually selects it; resolve its exact file/sheet/ranges before claiming it is connected. Never substitute a spreadsheet because an old example mentioned one. A saved report does not establish access to either source in the scheduled runtime.

Verify source access and a protected persisted-data writer separately, including access usable by a fresh scheduled task without the authoring session. Visitor connector consent is not an unattended credential. Use supported Site service access or a Site MCP tool and current identity restrictions; do not bake expiring credentials into the task. Before offering or creating a linked schedule, inspect the actual Site's linked automations and resolve missing metadata to avoid duplicates. Preserve paused state and existing audience.

Use the Sites skill's actual linked-schedule tools, not a standalone report task that loses the Site association. After publication call `get_site` for the user-owned Site and inspect `automations`. Missing/null automation metadata blocks a schedule offer/creation, not the Site handoff. For an accepted weekly plan with confirmed settings, recheck duplicates and use `create_schedule` only when no matching task exists. For an optional native offer, wait until the normal Site handoff and verified writer, then use `offer_site_schedule` with one complete day/time/timezone; button acceptance already creates and links the task, so do not also call `create_schedule`. Do not repeat a previous offer or decline. Preserve any existing paused state unless the user asks to resume. Keep any needed nonsecret refresh instructions with the Site so a fresh cloud task can recover the source/window/write/readback workflow.

Each authorized run fetches the selected source, validates totals, compares with stored evidence, saves only validated changes, reads them back, and sends only requested significant-movement/failure/action notifications. Routine data updates should use the verified writer, not rebuild/redeploy the Site on every run. Check the writer once through its intended unattended access before calling refresh ready; schedule creation alone proves neither an update nor delivery. If unavailable, deliver the persistent Site and report scheduling/update integration as incomplete.

## Optional visitor-connected mode

Only when the user explicitly requests on-open/manual Noibu reads for each viewer, use `dataMode: "visitor-connected"`. Read current Sites identity, app-integration, storage and server-runtime instructions. Select the connection in this order:

1. **Native Sites connector first.** Discover allowed Noibu plugin/connector IDs with pagination. When available, require native visitor consent, read-only declarations and per-request connection binding.
2. **Direct server-side OAuth when the integration is missing.** If completed discovery shows Noibu absent from the Sites connector list, check whether the approved Site runtime supports outbound Noibu MCP requests, OAuth callbacks, protected secrets, encrypted durable storage and trusted viewer identity. Where supported, use [direct OAuth implementation](direct-oauth.md) and its reusable server helper. Each viewer signs into Noibu separately; encrypted access/refresh tokens stay server-side, renewal uses refresh tokens, and every request uses that viewer's permissions. Never copy the creator's desktop/plugin connection or share their credentials with viewers.
3. **Explain the specific blocker.** If neither method is supported, state the actual missing capability or denied operation. Do not claim live data. A saved report remains **Saved snapshot — updates only when refreshed**; do not silently substitute a snapshot for requested live reads.

A missing connector integration is different from an explicit administrator/security restriction. A denied connector, policy-blocked egress, rejected approval or unknown eligibility is not evidence of a missing integration and must not trigger a bypass. Direct OAuth is a supported application connection, not a way around publishing permissions or security controls. Keep the Site permission preflight binding for either method.

Use [the read-plan helper](../assets/sites/site-report.mjs) and [Site client](../assets/sites/site-client.mjs) with a tested query-response normalizer. Store only a nonsecret `connectionMethod: "native-sites"` or `"direct-oauth"` alongside `dataMode: "visitor-connected"`; never credentials. Verify initial hosted reads, manual Refresh, token refresh followed by a provider read, each exposed filter, two-viewer account separation, and expired/revoked authorization. Record these observed checks using [the progress checker](../scripts/dashboard_progress.py); successful publication or one viewer's read alone does not prove readiness. Keep failures visibly stale and offer reconnect on an actual authorization failure.

Never silently migrate an existing Site to a different data mode or connection method; clarify material access/data-handling changes first. This optional path is not a prerequisite for publishing the saved report and does not itself provide closed-Site refreshes. Sharing a Site never shares the creator's Noibu connection. Visitor refresh tokens do not by themselves authorize unattended scheduled work.
