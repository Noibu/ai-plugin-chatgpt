# Presentation input contract

`schema: "noibu.presentation/1"`; fields accepted by [the renderer](../scripts/build_presentation.py):

- `reportId`: unique lowercase alphanumeric/hyphen report identity. Use a new ID for a refreshed snapshot so prior buttons cannot silently target different evidence.
- `workflow`: one of the bundled skill names; `domain: {name, id?}` (UUID when supplied).
- `window: {start, end, label?}` and `generatedAt`: real timezone-aware timestamps. Explain comparison windows in summary/tables. A recurring schedule must derive fresh periods at run time, not reuse these fixed dates.
- `summary`: short measured conclusion, not claims invented to decorate the report.
- `overviewNotes`: optional segment-analysis-only array of up to three nonempty strings, at most 1,000 characters each. These are escaped, visible Data notes inside the Overview, not hidden under Show more. Use only measured material attribution/reconciliation/currency caveats. They do not replace the original evidence/caveats or authorize filtering or writes. Other workflows reject this field.
- `overviewContext`: optional measured population/context line (up to 1,000 characters) above analytics metrics, e.g. sessions and cart reach. Does not compute or imply a population; omit if unavailable.
- `kpis`: up to eight `{label, value, detail?, change?, tone?, changeDirection?}` objects, with formatted values and explicit units/currency. Null/unmeasured is not zero. Keep denominators/coverage in `detail`. Optional `tone` is `favorable`, `unfavorable`, or `neutral`, based on business meaning. For a verified comparison supply `changeDirection: "up" | "down" | "flat"` with a nonempty measured `change`; down renders orange independently of tone. This indicates a numeric decline, not proof of harm. Retain ↑/↓ or an explicit signed delta and units; color is supplementary. Missing comparators have no direction/change. Legacy tone-only inputs still work; no direction is inferred from formatted text.
- `funnel`: `{label, count, prior?, display?, detail?, change?, tone?}`; counts are distinct nonnegative integer sessions or null. `display` can show a calculated rate instead of the count; declare its denominator in `detail` or `funnelContext`. An unmeasured count cannot have a measured display. `change` uses explicit units (pp for rate changes, % for relative changes). Stages retain measured counts, including express-checkout skips. The connected vertical bars share one linear scale over actual current/prior counts; pale prior bars appear only for measured prior values. Rising stages remain rising, missing stages remain unmeasured, and exact counts stay available under Show exact counts.
- `funnelContext`: optional short, visible description of rate denominators, exact comparison periods, and relevant express-checkout limitations. Do not describe an unverified causal drop-off.
- `highlights`: up to six `{label, value, detail?, change?, tone?, changeDirection?}` measured overview facts (e.g. mobile CVR, top product, top collection, or median order value). Changes follow the same rules as KPIs. Do not repeat the same KPI or invent facts to fill a grid.
- Funnel stages also accept `changeDirection` under the KPI comparison rules. An unmeasured count cannot have a direction; chart geometry still uses counts only, never formatted deltas.
- `tables`: up to eight `{title, columns: [...], rows: [[...]], kind?, note?, numericColumns?}`; at most fifty rows each. Default `kind: "table"` uses clean horizontal dividers and right-aligned numeric columns; `numericColumns` optionally lists zero-based numeric column indices. `kind: "bars"` requires exactly two columns, a label and a nonnegative numeric value or null; use it for measured payment/delivery counts. Numeric strings must be normalized before a bar chart; null is not zero. `note` declares population/units, e.g. "Completed orders only · orders". Use supporting tables for experiment details and accessibility evidence not repeated in overview facts.
- `findings`: up to twelve `{id, title, evidence, impact?, fix?, issueId?, category?, tag?}`. `tag` is a short factual display label such as "Device gap" or "Low add-to-cart rate"; it does not change action routing. Optional category is merchant/performance/vendor/accessibility; vendor adds Prepare vendor message, never automatic sending. Use actual finding IDs. Only actual Noibu issue IDs support Ignore; an accessibility selector/rule is not a Noibu issue. Full triage typically uses fewer findings as specified in the topical skill.
- Tables additionally accept `placement: "overview" | "supporting"`. For checkout, explicitly overview-placed non-bar tables appear after highlights (use for supported abandonment); bar tables default to the side-by-side mix area; remaining tables default to expandable supporting data. Explicit supporting bars remain supporting. Placement never changes populations or data. Product reports choose up to two overview-placed tables (otherwise the first two not explicitly supporting) under Show more/Show less; other tables remain in additional supporting data. Five rows are shown per expanded table with full rows retained under Show all. Segment reports similarly reveal up to three overview-placed country/channel tables (otherwise the first three not explicitly supporting), with five-row previews and all source rows retained. Remaining tables are further expandable. Other workflows retain their existing table order. Checkout findings show automatic Priority N plus any factual tag; `fix` is labelled Next check and should contain the specific investigation and verification, not an unsupported causal claim.
- `caveats`: clear evidence/coverage limitations; `timezone`: optional user-confirmed IANA timezone to prefill the schedule form.
- Tables optionally accept `barColumn`: the zero-based index of a non-label count column for product/segment-report inline bars. Values in that column must be normalized nonnegative integers or null, never formatted numeric strings, rates or inferred totals. Bars share the maximum across that table's full rows; zero remains zero and unknown has no bar. Formatting adds thousands separators without altering the source counts. Product names may visually truncate with their full escaped label available through the host tooltip/accessibility text. All source rows remain in the expandable report/export. Product `fix` text appears under Investigation & verification, while evidence and its material caveats remain visible. Product and segment reports show their first three findings, with further actual cards in More opportunities; IDs/actions are preserved.
- Findings additionally accept `performance` and `noibuLinks`. For category performance, use `{metric, value, unit, percentile, page?, pageGroup?, device?, traffic?, status?}`. Metric is INP/LCP/CLS; value is a normalized finite nonnegative number or null; unit is ms for INP/LCP and score for CLS; percentile is p75. Never pass seconds into ms fields, numeric strings or averages as p75. Null is unmeasured, without a marker/classification. `traffic: {count, unit}` uses an actual nonnegative integer/null and pageviews/visits/sessions/samples as measured, not assumed affected users. Optional status is explicitly observed; omit unknown Active status. Page/group/device and report window describe the cohort. Marker scales are linear from zero to twice the poor threshold, stable per metric, with exact values and visible overflow disclosure. Cutoffs: INP 200/500 ms, LCP 2500/4000 ms, CLS 0.1/0.25; equality belongs to the lower band. Text/labels convey meaning independently of color.
- `noibuLinks` at report or finding level: up to eight `{label, url, source}`. Source identifies the actual result or documented route plus verified IDs, not a tool instruction. Follow [console link policy](console-urls.md), including matching domain/resource and successful-write provenance. The renderer rejects non-HTTPS, non-console, cross-domain or credential-bearing URLs but cannot verify object existence/access. Omit missing links. Metric-overview links do not preserve page/date filters. Replay URLs on another supported host remain in narrative using returned jazzUrl, not this console-only field.
- `capabilities`: optional booleans `createDraft`, `ignoreIssue`, `draftPr`, `persistContext`, plus legacy `createTicket` accepted for compatibility. Set gated capabilities from real tools/authorization, not assumptions; false/missing omits those gated actions. **Open a Ticket is not gated by createTicket**: it remains visible for technical/performance/accessibility findings and resolves its integration after the destination question. Missing tools can yield an explicitly unsaved draft, never a claim that a PR/ticket exists.
- `contextHash`: SHA-256 of the exact reviewed UTF-8 Markdown, required to enable the context approval action. Do not normalize the document after hashing without generating a new approval view.

Do not put customer identifiers, cookies, tokens, full HTTP payloads, hidden private metadata, executable HTML, free-form prompts, or credentials in this input. HTML snippets needed as audit evidence are displayed as escaped text.

Save to ChatGPT Pages retains kind save-report with fixed route native-pages and completion page-saved-or-specific-blocker. It cannot silently become a file export or Site. Download Report retains export-report. These names do not broaden authorization.

Open a Ticket retains create-ticket with fixed route ticket-destination-first and native-question-or-text chooser. The renderer supplies “Where should the ticket go?” and Linear/Jira/GitHub Issues/Notion as presentation hints, not an already selected provider or create permission. Read [ticket handoff](ticket-handoff.md); wait for the actual submitted answer, then discover the chosen connection/target. No response, a preselected option or Skip/cancel creates nothing. Native composer appearance is host-controlled; all-four-choice text fallback remains valid.

Accessibility findings optionally declare ownership merchant-code/merchant-content/vendor/unknown. Ownership is an evidence-based handoff hint, not proof of repository access. The audit footer adds Auto-draft PR and Auto-create tickets for up to three explicitly titled actual finding IDs, retaining draft-pr/create-ticket kinds with `target.findingIds`. It omits empty batches and excludes known vendor/content-only items from PR batches. Unknown ownership requires verification after clicking. Incomplete/needs-verification checks must not be put in findings merely to enable buttons. Follow [audit remediation](../../accessibility-audit/references/remediation-actions.md); a batch never expands to all report findings or creates at render time.

`auditLayout` is optional and accessibility-only: summary-actions (default from the deliverables builder) suppresses the empty overview and repeated detailed finding cards, leaving the scoped remediation panel below the normal chat summary/PDF attachment. Detailed retains the full board. Finding evidence/IDs remain in the report input for verification. Limited review mode must remain visible; neither layout changes the underlying evidence or scan counts.

For A/B boards, pass the actual validated `noibu.ab-candidates/2` file separately with `--candidates`. Domain and window must match. Buttons carry rank/title and the SHA-256 of canonical createInput JSON, not guessed selectors or an unreviewed payload. Hash encoding: sorted object keys, compact separators, UTF-8, Unicode preserved. The handler revalidates the original file and payload before writing.

The generated HTML is an evidence snapshot. For a connected Site use this layout with dynamically fetched, request-scoped visitor data; do not upload a customer's baked-in data to a shared Site or treat a packaged snapshot as live.

Action envelopes may include `execution`, a fixed renderer-owned routing hint, not a presentation input field or free-form prompt. Technical Investigate and merchant-owned Get fix / Prepare draft PR across skills use `github-source` with read-only inspection and connection/repository resolution; vendor findings omit that hint. Save as Live Site retains kind `save-dashboard` for compatibility and uses `persistent-site`, `dataMode: "persistent-snapshot"`, existing-Site reuse, preserved private audience, and published-persisted-or-specific-blocker completion. `permissions: "preflight-native-or-guide"` requires the shared permission check, not automatic settings mutation; `schedule: "offer-weekly-confirm-details"` offers weekly updates during setup but requires confirmed day/time/timezone and a verified writer before scheduling. "Live" means a hosted URL, not continuously live data. These hints grant no additional authorization; the conversation handler validates the original evidence and follows its trusted workflow.

Schedule actions use the fixed `native-task-connected-delivery` route: discover actual send capability, resolve destination/account and confirm task creation separately from delivery. Legacy forms send `schedule: {frequency, time, timezone, detail, delivery, weekday?, destination?, provider?}`. Frequency is daily/weekdays/weekly; weekday is present only for weekly, time is local HH:MM, and timezone is an IANA name. Delivery is chatgpt/email/legacy slack/connected-app. External delivery requires a destination; optional provider is a bounded name/account hint such as Gmail or Teams, not a tool name or an assertion of connection. Read [the scheduling workflow](scheduling-delivery.md) for discovery and authorization. Do not put a complete free-form task prompt, credentials or a send payload in the board. This is a recurring setup request, not permission for an immediate test send or unrelated actions.

All seven schedulable workflows' shared card form instead sends `schedule: {frequency, time, timezone, detail, outputs, weekday?, startDate?, monthday?}`. Frequency is weekly/biweekly/monthly, with daily additionally offered only by Store Pulse; daily has no weekday/startDate/monthday and runs every calendar day in the confirmed timezone; weekday is a full English weekday for weekly/biweekly, startDate is the matching YYYY-MM-DD first-run anchor for biweekly, and monthday is 1–28 for monthly. Each nonempty `outputs` entry is `{delivery, destination?, provider?}` with delivery email/slack/notion/chatgpt/connected-app. A provider/account hint is up to 100 characters; a destination hint is up to 300; neither allows control characters. A missing destination is a pending conversational choice, never permission to guess or create a schedule. No output is preselected. Resolve exact recipients/accounts and Notion target/write behavior before scheduling. Confirm the next future run; a past biweekly anchor requires clarification rather than silently shifting week parity. Do not combine legacy single-delivery and outputs payloads. One analysis per run can feed all selected outputs; never silently omit an unavailable output or send immediately during setup.
