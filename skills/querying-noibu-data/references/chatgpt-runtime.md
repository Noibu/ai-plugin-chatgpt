# ChatGPT runtime adapter

Load this shared reference for outputs, browser work, exports, scheduling, and optional external actions. These instructions supersede inherited presentation and integration assumptions in the data references.

## Connection and skill resources

Use this plugin's Noibu connection and native Connect/sign-in flow. The verified service endpoint is https://mcp.noibu.com/mcp; app-backed releases retain their registered connection rather than creating a second direct-URL MCP server. No CLI or Codex installation is required. An expired token needs native reconnection, not pasted credentials. Resolve resources relative to the packaged skill directory. If a reference cannot be loaded, use the current tool schema and this guide; do not claim it was read.

## Output

Full reports use [native presentation](presentation.md) for KPI/funnel/priority boards and supported conversation action buttons. Keep useful prose and accessible tables, and fall back to them when the native renderer is missing. No Claude widgets, slash commands, task lists, connector UUIDs, or Cowork artifacts are required. A follow-up such as "investigate this signal" uses prior evidence and retrieves only new depth. A button sends a user-approved request to ChatGPT; successful host submission is not proof the backend action completed.

A saved report is a timestamped snapshot. **Save as Live Site** publishes that report into a private Site with D1-backed snapshot/history persistence through [the Sites workflow](connected-dashboard.md); it does not imply a live data feed, visitor Noibu consent, or a schedule. Show data timestamps and freshness honestly. Scheduled source reads, totals checks and persisted updates are a separately requested, verified capability. Visitor-connected Noibu reads/Refresh remain an explicit optional mode, not a publication prerequisite. Do not label a local file/Page a published Site. An optional MCP App UI requires actual tool/resource metadata and server implementation; a skill's HTML does not create one.

Every Site save/resume starts with [the permission preflight](site-permissions.md). Use supported scoped approvals when possible; otherwise give current-chat permission-selector instructions, including optional reviewed Custom configuration for non-managed local setups. Never silently modify security settings or automate their UI. Offer weekly fresh-data updates during Site setup, confirm day/time/timezone and notification intent before scheduling, and verify the unattended source/writer. A scheduling choice or missing updater must not block publication of the current report.

## Files and exports

Use file creation/export tools available in the user's ChatGPT session when a download is requested. Write only to the task's supported artifact/output location. Include domain, window, generation time, methodology, currency, and limitations; reuse prior evidence unless refresh was requested. Never save customer data into the installed skill directory. A generated standalone HTML report is static and contains no credentials or direct MCP calls. PDF creation is optional and requires the actual available document/PDF tools; render and inspect if those tools allow it. If a format is unsupported, deliver the report inline or in an available format and say which was produced.

## Browser

Detect the browser capabilities in the current session; read their documentation and any matching available browser skill before acting. Use ChatGPT's supported browser-control API, never Claude browser tool names. A local Chrome session needs ChatGPT desktop and its extension, but can run in ChatGPT Work without selecting Codex. The built-in desktop browser uses a separate profile. The cloud browser does not inherit local cookies/tabs/extensions; availability and sign-in vary by plan/workspace.

Use actual rendered evidence, page text, and screenshots through supported APIs. Read-only evaluation must remain read-only. Arbitrary JS injection, axe-core execution, DOM/CSS mutation, device emulation, or CDP access must be explicitly supported and authorized; do not infer those capabilities from ordinary click/screenshot support, and do not bypass unavailable operations through hidden APIs or a separate automation channel. Web search/page fetching is suitable for public policy text but does not prove rendered control placement or execute an accessibility scan.

Live cart walkthroughs require the user's request to cover them. Use a dedicated test session when possible. Record cart contents first, add at most one agreed/in-stock item, and remove only the item added by this workflow. Never clear a pre-existing cart. Confirm restoration, or explicitly report what could not be restored. Do not fill personal/payment information or place orders.

Before/after previews must use the same viewport/scroll position and observed site facts. Mutations stay within a temporary preview context and are reset/reloaded afterward. Without a browser or supported mutation/capture/export, complete the report without visual previews and explain why they were omitted; never present a fabricated screenshot or stock mockup as a live storefront capture. Browser accessibility scans similarly require approved axe execution; no hosted backend-reader dependency or automatic remote job fallback is part of that workflow.

For an accessibility audit blocked by read-only evaluation, read [audit execution setup and review](../../accessibility-audit/references/execution-and-review.md). Guide the user's allowed Browser Developer mode/site-approval setup and rediscover the actual execution API; terminal permissions do not unlock browser scripting. Unless the request is axe-only, continue a distinct limited browser-based review using supported inspection. Preserve the selected URLs/window, keep automated counts unknown and manual coverage separate, and never run axe in a read-only evaluator or use alternate channels to bypass a denial.

## Scheduling

For every scheduling request read [provider-agnostic scheduling and delivery](scheduling-delivery.md). Only schedule when requested. Discover the native scheduler, Noibu access and the selected connected app's actual send capability; resolve sender/account and destination before setup. Use a recurring ChatGPT task that fetches fresh data then sends through the chosen provider on each run. Do not require a provider-specific recurring scheduler or treat a read-only connection as sending access. Email can use Gmail, Outlook or another connected send-capable provider; messaging can use Slack, Teams or another supported app. Preserve the user's provider choice and native approvals; never silently weaken permissions or fall back to a different destination.

Inspect matching tasks where supported, preserve paused state, and actually create/update the authorized task through the scheduler after resolving prerequisites. Retain exact time/timezone, fresh rolling/comparison rules, optional blocks and delivery scope. ChatGPT is the default output only when selected; an explicit external destination is not replaced by it without acceptance. Monitor-only silence/significant-change behavior applies when requested, not to every recurring report. Keep credentials out of task prompts. Confirm task creation separately from untested delivery, and report the exact missing tool/connection/approval or actual error instead of a generic inability to verify. No browser cron, blind retries, Claude scheduler APIs, or invented Noibu scheduler.

## Optional integrations

Analytics works with Noibu alone. GitHub, a commerce admin, ticket tools, or email/Slack are only needed for a separately requested action. Discover available tools and obtain the destination/account/scope required for that action. If absent, present a useful copyable ticket, vendor message, patch, or implementation specification; do not block the analysis.

For any merchant-owned technical investigation, requested code fix, accessibility remediation, performance fix, A/B variation implementation or draft PR, use [the shared GitHub handoff](../../tech-diagnosis/references/github-handoff.md). Reuse and verify an existing connection/repository/ref; otherwise present the native Connect/reauthorization or exact plugin-discovery suggestion and ask for the repository. Do this for natural-language requests as well as buttons, before claiming source-verified code or file/line references. GitHub is optional for analytics, browser scans, generic guidance and Noibu draft creation; keep that useful work available while connection is pending. Vendor/platform-owned code uses its supported owner handoff, not an unrelated merchant repository. Repository writes/PRs require separate requested scope and native approvals; no automatic merge/deployment. Sites' managed source upload is unrelated to this storefront GitHub gate.

Do not send external messages, create tickets/PRs, merge, deploy, alter issue state, or start/stop tests as a side effect of a report. Use server-returned IDs and links after successful actions. For ambiguous write outcomes, read the existing objects before retrying; duplicate drafts and jobs are possible.
