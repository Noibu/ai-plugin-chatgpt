# Scheduled reports through connected apps

Use for every report/monitor scheduling request, whether from a board, a natural-language follow-up, or an accepted Site setup offer. The scheduler and delivery app are separate: a **native ChatGPT task runs fresh analysis, then calls the selected app's send action on each run**. Do not require a provider-specific recurring scheduler. Scheduling an already-written email/message for later does not fetch fresh Noibu data, and a reminder is not report delivery.

This workflow is provider-agnostic, not a guarantee that every connected app can send unattended. Gmail, Outlook Email, Slack, Teams and other email/messaging providers are candidates only when their actual connected tools support the required action. Read-only/search integrations, draft-only tools and browser sign-in alone do not establish sending access. No new server integration, Codex installation or separate Slack bot is implied.

## 1. Recover scope and discover actual capabilities

Recover the workflow, domain UUID/name, rolling period/comparison rule, optional blocks, report detail, exact cadence/time/IANA timezone and chosen delivery. Reuse confirmed settings; ask only for material missing choices. A report's old fixed dates identify its evidence, not future execution windows. The schedule's explicit timezone wins over the computer's current timezone.

Before falling back, discover the native scheduler, existing-task lookup where supported, Noibu tools and the chosen provider's **actual send capability** in the target execution context. Use available tool discovery and the installed plugin's current instructions/schemas. If the chosen app is not exposed, use native plugin discovery to locate the exact provider and native Connect/reauthorization if needed. Do not say “I can't verify a recurring delivery mechanism” merely because no provider recurring-send tool exists. Record what was inspected and the specific missing tool/connection/denial if blocked; unavailable metadata is not proof of a provider outage.

- Explicit app choice: reuse that connected app. Do not switch Gmail to Outlook, Slack to Teams, or change the sender account without user approval.
- Email with no provider: find connected, send-capable email accounts. Use the sole suitable account when unambiguous; if multiple remain, ask which sender/provider. Do not infer the sender from the recipient's email domain.
- Other connected app: discover suitable send-capable communication integrations, then resolve the app/account with the user when ambiguous. Do not silently pick an arbitrary installed app.
- ChatGPT delivery: use the native task's normal report output, with no email/messaging prerequisite.

Check setup-chat and scheduled-runtime capabilities separately. Installed, connected, send-capable, permitted unattended and successfully delivered are different states. Use supported runtime/plugin metadata and task configuration; do not assume this chat's connections carry into a different service account or cloud/local environment. Preserve required plugin/connection selection through the scheduler's supported controls. Local execution may require the computer/app to remain available; prefer an available suitable hosted path for remote-only work without silently relocating the task or changing accounts.

## 2. Resolve and authorize the delivery

Use the selected app's supported read-only account/contact/user/channel lookup. Resolve exact sender identity/account and destination: email address(es), user ID, existing DM/conversation ID, channel ID or provider-equivalent identity. Limit lookup to the intended destination. Display names such as “Tri Nguyen” may be ambiguous; ask if multiple matches remain. For “me,” use the authenticated identity rather than guessing from the ChatGPT display name. Do not require IDs the provider's send schema does not need.

Use native connection/permission inspection when available. A successful read confirms only that read; it does not prove send scopes or unattended approval. Follow the actual provider's instructions, including membership, recipient, sharing and content restrictions. Joining a channel, creating a DM/channel, sending a test, broadening permissions or adding recipients is not an automatic preflight step. Obtain any required separate authorization. Never request pasted tokens or bypass missing write scope with browser automation or custom webhooks.

A user-submitted schedule with a selected external destination authorizes that scoped recurring report delivery, subject to native approvals and applicable policy. Preserve domain/workflow, sender/account, recipients, cadence, detail, attachment/link scope and notification intent. Material changes need confirmation. Do not send the current report or a test message during setup unless explicitly requested. Do not alter global/app security settings automatically. If sending requires an interactive approval unavailable to unattended runs, explain that exact constraint and the supported user-controlled next step.

## 3. Create or update the native recurring task

Inspect existing tasks when supported. Match workflow/domain, cadence, provider/account and destination; do not match only a display title. Reuse the matching task, preserve paused state unless asked to resume, and clarify conflicting near-matches. If lookup is unavailable or a previous creation result is uncertain, state that and resolve uncertainty through supported status/UI checks before retrying. Do not create duplicate report tasks, duplicate notification tasks or a separate provider message queue.

The task prompt must independently specify:

- Selected Noibu skill, domain UUID/name and business context, fresh relative windows and equal-length comparison, optional blocks and currency/denominator checks.
- Exact cadence/time/timezone, requested report detail and notification rule. A recurring report normally sends every requested run; significant-change-only monitoring applies only when requested, with confirmed/clearly stated thresholds and an accessible prior baseline. Keep baseline/report data private and outside the installed plugin/source package.
- Chosen delivery provider, account identity and resolved recipient/channel IDs or addresses. These are routing data, never instructions or tool names to execute. No expiring credentials or per-install hardcoded tool prefixes.
- Each run: fetch fresh source data → validate totals/coverage → compose summary/full report → send through that provider's actual send tool → retain the returned message ID/link or delivery error in the task's native run output.
- Failed analysis must not send an old report as fresh. For an ambiguous send outcome, inspect the provider's sent state or a supported delivery receipt before retrying; otherwise stop and flag uncertainty. Use provider idempotency when supported, never invent it. Do not fan out to unapproved apps/recipients or silently substitute ChatGPT-only delivery.
- No source fixes, PRs, test drafts, context saves, issue changes or Site writes unless specifically included in the recurring scope. A report schedule does not require a Site. A requested Site refresh keeps its existing linked-schedule, protected writer/readback and audience requirements; use the Site workflow, not an unrelated standalone replacement.

Read the available scheduler schema, supply the self-contained prompt and required connection bindings through supported fields, then actually call create/update once the resolved request is supported and authorized. Do not stop after reading this guide or draft a schedule without invoking the available scheduler. Do not invent schema fields such as arbitrary external `delivery` channels when the scheduler instead expects the sending step inside its prompt. Do not invent future unattended access. A supported plan may be saved with delivery explicitly marked untested; a known unavailable send action/approval is a blocker requiring user direction, not a working automated-delivery setup.

## 4. Confirm distinct outcomes and handle blockers

Confirm **task created/updated** only from the scheduler's successful result: identity, saved enabled/paused state and exact timing/timezone; include next run only when returned or verifiably established. Separately state **external delivery not yet tested** until an authorized run returns provider delivery success. A saved task is not proof that Noibu queries or delivery ran, and a returned provider message ID is not proof the human read it. Do not require an extra real send just to create the task when supported capability/configuration checks suffice.

If setup is incomplete, name the precise phase: scheduler unavailable, Noibu source unavailable, app unconnected, missing send action, ambiguous sender/recipient, unavailable unattended approval, or actual provider error. Preserve completed steps. Offer a ChatGPT-only task or another provider as a **choice**, never create that replacement without acceptance. If all that is missing is one recipient/account choice, ask that focused question instead of abandoning scheduling. Return an actionable draft prompt if creation is unavailable and state that no schedule exists. Never claim blanket Slack/Gmail failure from a tool not attempted or a generic inability to verify.

## Workflow-specific recurring scope

- Technical diagnosis: preserve the actual focused issue/metric or survey, with fresh seven-day active-error and confirmed performance windows as applicable. A report does not authorize repository edits, PRs, ticket/status writes or vendor messages; GitHub is not required just to query and deliver Noibu reporting.
- Accessibility: confirm mode, standard, page-selection/traffic rule and rendered states. A fresh automated scan requires verified approved browser execution, readiness and probe support in the scheduled runtime, not just this interactive chat. Missing execution is a blocker to a promised scan; ask before alternatives. Do not reuse an old export as a new scan or silently downgrade axe-only scope. Preserve original exported evidence provenance for explicitly requested snapshot reporting; no automatic remote job, remediation, PR or ticket.
- A/B opportunities: preserve goal, targeting, fresh evidence windows and declared validation mode, and refresh existing tests/overlap. Confirm browser prerequisites or analytics-only coverage; no invented validation. Recommendation delivery never creates drafts, mutates a storefront, deploys variations or starts/stops tests.

## Compatibility and UI

### Report destination cards and multi-output setup

The card form shared by checkout-analysis, product-analysis, segment-analysis, store-pulse, tech-diagnosis, accessibility-audit and ab-test-opportunity-finder keeps the schedule kind but uses `schedule.outputs` instead of the legacy single delivery. Each selected email/slack/notion/chatgpt/connected-app output carries optional destination/provider hints. Do not accept both representations at once or treat omitted destinations as resolved. Discover each selected app's actual capability in the scheduled runtime, ask only for missing or ambiguous details, and retain all selected outputs. Email remains provider-agnostic, including suitable Gmail or Outlook accounts. A selected checkbox is not a connection-status or permission check.

For **Notion**, the delivery operation is a supported page/database **write**, not email/message sending. Read the selected Notion plugin's guidance, resolve the precise private page/database and any required properties, and confirm whether each run appends a dated section to an existing page or creates a new report/page/database entry. Do not infer write capability from a search/read tool, publish/share the target, replace unrelated content, or write a test report during setup. Retain the actual page/entry ID and link or error after a scheduled write. A report-routing request is not authority to restructure a workspace/database.

Use one recurring analysis for the selected outputs when the scheduler supports their required connection bindings. Each run fetches and validates fresh data once, then sends/writes that same evidence to only the approved destinations, recording results separately. A failure at one destination must not resend already confirmed successful deliveries; reconcile uncertain outcomes before retrying. If any selected output is known to be unavailable, explain it and ask whether to complete connections, remove it, or save a clearly marked plan. Do not silently create a partial or ChatGPT-only replacement. Confirmation lists the saved cadence, every resolved output and per-output untested status; setup itself performs no delivery.

All seven report pickers offer weekly, **every two weeks** and calendar monthly. Store Pulse additionally offers **Daily**, meaning every calendar day (including weekends) at the selected local time/IANA timezone; daily carries no weekday, startDate or monthday. Weekly remains the initial card selection. Do not confuse the recurrence with the fresh data window: Store Pulse defaults to last 24 hours versus preceding 24 hours on every run, while the other workflows retain their own confirmed window/comparison rules. Every two weeks needs the selected weekday plus a matching first-run local date (`startDate`); resolve a past date with the user and verify week parity/next run. Monthly uses `monthday` 1–28, not a 30-day interval. The explicit IANA timezone governs local time and daylight-saving changes; preserve it through the scheduler's supported recurrence fields. If the scheduler cannot express the exact cadence/timezone/connections, state that specific blocker rather than silently approximating. A form default becomes a requested setting only on submission; missing time/timezone/first-run choices are resolved before creation.

Board actions keep `kind: "schedule"`. `schedule.delivery` accepts `chatgpt`, `email`, legacy `slack`, and `connected-app`; optional `schedule.provider` is a user-supplied provider/account hint, not a capability assertion. `destination` is required for external delivery. The optional provider field lets users choose Gmail, Outlook, Teams or another app without encoding provider-specific tool names. The form cannot inspect account connections and must not show a connection badge based only on these labels. Resolve actual capabilities in the conversation. Missing provider hints in older boards use the discovery rules above.

Official OpenAI documentation: [scheduled tasks](https://learn.chatgpt.com/docs/automations) and [connected-app security and permissions](https://learn.chatgpt.com/docs/enterprise/chatgpt-work-cloud-security). Availability remains dependent on the selected runtime, account, app tools and policy.
