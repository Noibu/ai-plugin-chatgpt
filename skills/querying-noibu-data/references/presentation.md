# Native ChatGPT presentation and actions

Use this layer for full reports and explicit visual requests. Focused factual questions can remain brief text. Keep the user's existing analysis scope, measured numbers, and limitations; visuals do not authorize extra scans, writes, or schedules.

## Select the surface

| Outcome | ChatGPT surface |
| --- | --- |
| In-chat overview, funnel, ranked signals, or experiment choices | Native inline visualization with the packaged board and action bridge |
| Saved editable report snapshot | Private Page; CTA Save to ChatGPT Pages |
| Downloadable report snapshot | Verified PDF/file (printable HTML fallback); CTA Download Report |
| Reopenable saved analytics dashboard | Private persistent Site with verified D1 snapshot/readback; CTA Save as Live Site |
| Explicit per-visitor live connector reads | Optional visitor-connected Site after eligibility, consent and provider reads are verified |
| Recurring analysis | Native ChatGPT scheduled task, independent of a saved dashboard |

Discover the actual visualization/file, Pages, Sites, and scheduling capabilities. Read their current instructions before using them. Do not require Codex, a specific connector instance name, or a server UI change. Do not register a fake MCP UI resource: this layer uses native visualizations and conversation follow-ups, not a newly deployed MCP App.

## Default report compositions

- Use the screenshot-inspired Noibu report design: rounded overview panels, tabular KPI values, restrained labels/dividers, neutral connected vertical funnels, compact aligned tables, and spacious finding cards with a tag, impact, title, evidence, and Investigate ↗. All four analytics reports use checkout’s light outlined composition: background-colored content, thin borders, subtly tinted headers and unfilled KPI groups; other reports retain soft-neutral panels. The outer conversation remains transparent. Retain the host's native button and focus behavior; no external fonts, icons, or network dependencies. Colors adapt to light/dark mode. This explicitly requested report composition may use five KPI tiles and report panels; do not flatten it into a generic unframed chart or substitute a prose-only report when native rendering works.
- Store Pulse: one or two summary sentences, unfilled Sessions / Engagement / Conversion / AOV / RPS groups when measured, five-stage connected purchase funnel with rates against total sessions and pp/relative deltas, optional requested blocks, a dedicated Save as Live Site row at the bottom of Overview before any opportunities, and a separate final Download & schedule footer with Pages / Download Report / Schedule report.
- Checkout: screenshot-style thin-bordered Overview with muted header, compact metrics and neutral connected cart → checkout → payment → completion funnel, visible denominator/comparison context, completion/device/value highlights, explicitly placed observed-abandonment table, and side-by-side payment/delivery bars only for actual populated counts. Supporting data defaults to an expandable section. Save as Live Site sits at the overview's bottom-right; numbered opportunity cards retain evidence and a concrete Next check with Investigate. Download Report / Schedule report finish the report, with Save to ChatGPT Pages still available as the separate snapshot option. Missing slices stay omitted.
- Products: outlined Overview with compact metrics and a measured neutral view → cart → purchase funnel (name a focused cohort; never call it global). Show more/Show less reveals the top product/collection tables with five rows, optional normalized session bars and full-label access; additional tables/rows remain expandable. Save as Live Site sits within the overview. Show up to three tagged investigation opportunities first, retaining measurement caveats and an expandable investigation/verification plan; further real cards appear under their actual count. Download & schedule contains Download Report / Schedule Insights and the separate Pages option. Omit unmeasured stages rather than invent a funnel.
- Segments: outlined Overview with site-wide/mobile/desktop CVR and session denominators, a few supported highlights and visible material data notes. Show more/Show less reveals three country/best-converting-channel/most-visited-channel tables (five rows each; all rows retained), with supporting history/campaign/landing data further expandable. Save as Live Site sits within the overview. Up to three concise tagged opportunity cards have Investigate and expandable investigation/verification; any further real cards retain their actual count. Download & schedule contains Download Report / Schedule Insights and the separate Pages option. Preserve peer/intent/traffic-mix distinctions, currency components, bounded ranks and count discrepancies; no forced funnel or invented device regression.
- Technical survey: separate merchant/performance/vendor sections. For measured p75 INP/LCP/CLS use screenshot-inspired performance cards: metric/status header (only observed status), plain-language title/evidence, large value, green/amber/red threshold bands with a measured marker and labelled cutoffs, actual traffic unit/page/device/window, Get fix ↗ and verified Noibu metric link. Populate the contract's structured performance field, not a prose-only gauge. Missing values get no marker or verdict. Retain Investigate, Ignore only for actual issues, optional PR/ticket actions, export/schedule. Focused diagnoses also use measured metric cards but show the proposed fix immediately, not only behind a button.
- Accessibility: for axe, actual completed findings and automated severity summary with incomplete/failed/unscanned coverage separate. If only a limited browser-based review is possible, label the mode prominently, show reviewed/unreviewed pages and evidence-backed manual observations separately, and keep axe scan/severity counts unknown rather than zero. Do not pretend native snapshots are axe findings. Get fix / Investigate and scoped optional PR/ticket actions remain available. Scheduling declares its mode and verifies the required browser/execution in the future runtime; no silent downgrade of axe-only work.
- A/B opportunities: ranked test sections with change/hypothesis, measured evidence, traffic, control/variation setup, metric/guardrails/targeting/overlap and developer handoff. Attach the validated candidates file. Create A/B draft in Noibu selects exactly one candidate; no render-time writes or lifecycle advancement. Browser screenshots remain optional.
- Business context: present the actual reviewable context inline or on a Page; optionally add a save-approval action tied to its exact content hash. No implicit persistence.
- Shared query/Setup: no mandatory chart. A requested funnel or connection summary may use the same layer, without incidental schedules or writes.

All analytics reports keep Save as Live Site in a dedicated bottom-right row after dashboard content and before investigation cards. Final Pages/download/scheduling controls do not repeat it. Use explicit measured `changeDirection` on KPI, funnel and highlight comparisons to render numeric declines orange; retain units/arrows and business interpretation separately. Missing comparators stay unknown; captions are not changes.

## Build and render

Read [the input contract](presentation-contract.md), then use [the renderer](../scripts/build_presentation.py) with measured data:

```text
python <packaged-skill>/scripts/build_presentation.py <task-output>/report.json --output <task-visualization>/noibu-report.html
```

For experiment boards add `--candidates <task-output>/candidates.json`; the existing candidate validator runs first. For a standalone downloadable snapshot add `--standalone` and put it in the task output directory. Helpers use only the Python standard library. Never save runtime reports in the installed skill directory.

Render the fragment through the target's documented native inline visualization mechanism, not as an HTML code block. In runtimes supporting the visualization content-reference format, use `visualize{"path":"<actual absolute generated path>"}` in the final response. If the host prescribes a different mechanism, follow it. Load the available visualization skill and adapt host styling/API details before rendering. A generated file alone does not prove in-chat rendering.

The packaged [board template](../assets/presentation/board.html) and [action controller](../assets/presentation/actions.js) can be adapted directly if file/script execution is unavailable but native visualization authoring exists. Keep all data escaped and preserve fixed action kinds, evidence identity, and capability detection. Include actual controls, not decorative mock buttons. Do not use arbitrary model-supplied JavaScript or action prompts.

All seven workflows with a Schedule report button (checkout, product analysis, segment analysis, Store Pulse, technical diagnosis, accessibility audit and A/B opportunities) share the [schedule selection template](../assets/presentation/checkout-schedule.html) and [local schedule controller](../assets/presentation/checkout-schedule.js). The renderer includes these automatically for all seven schedulable workflows, with a workflow-specific heading; do not substitute the legacy single-destination dropdown. Frequency/day/time and Email/Slack/Notion selections are local until submitted. Multiple selected outputs remain one recurring report request, with destination/account resolution and actual send/write checks in chat. These labels never claim an app is connected. The same weekly/every-two-weeks/monthly choices apply to all seven; Store Pulse alone additionally offers Daily (every calendar day, including weekends). Weekly remains the initial selection, so a new option does not change existing preferences or tasks. Setup, business context and shared query workflows do not gain schedule buttons. Existing single-destination action payloads remain supported for older boards. Technical reporting never implies fixes; recurring audits must verify scheduled-runtime browser execution; A/B scheduling produces recommendations, not drafts or test activation.

The fixed [Noibu report stylesheet](../assets/presentation/report.css) provides the shared appearance and checkout/product/segment/Store Pulse outlined skins; the renderer scopes it to each report identity. Use this design instead of restyling each invocation. At narrow widths the funnel becomes labeled horizontal stage rows, metrics wrap, selection cards reflow, and action groups wrap without clipping. Use Show exact counts for numerical inspection; keep material caveats visible by default. Visual resemblance does not justify ambiguous denominators, tiny gray text, fabricated prior bars, or monotonicized data.

Buttons feature-detect the host's follow-up-message bridge. They send a structured request to ChatGPT; the visible acknowledgement says only that the request was sent. The model handles the actual save, export, investigation, write, or native schedule with its authenticated tools. No credentials or direct MCP network calls are embedded. Presentation-only controls stay local.

Schedule report uses [provider-agnostic scheduling and delivery](scheduling-delivery.md): native ChatGPT recurrence plus a connected provider's actual send action per run. Email and Other connected app allow an optional provider/account hint, so users can choose Gmail, Outlook, Teams or another send-capable app without a provider-specific UI release. Slack remains a compatibility shortcut. These labels are not connection-status checks. Resolve actual accounts/recipients and unattended sending capability in the conversation; no test send or automatic permission change is authorized by the form.

If rendering or the bridge is unavailable, finish the useful report as text/tables. The standalone board reveals a copyable action request instead of silently failing. State that copying/submitting a request is required and nothing has been created. Reuse prior query evidence for exports; refresh only when requested or necessary for safe write validation.

## Handle action requests

Full accessibility audits default to a real attached PDF and concise chat summary from the same normalized results, plus Auto-draft PR / Auto-create tickets for visibly selected top findings. Follow [audit report](../../accessibility-audit/references/report.md) and [remediation](../../accessibility-audit/references/remediation-actions.md). A limited browser review keeps unknown axe counts; PDF availability does not authorize unsupported scans. Empty/unconfirmed findings get no batch remediation actions. The report file/board does not itself create a ticket or PR.

Technical/performance/accessibility finding cards always show **Open a Ticket**, regardless of connected-ticket capabilities. Its [destination-first workflow](ticket-handoff.md) asks “Where should the ticket go?” through the native user-question/composer UI with Linear, Jira, GitHub Issues and Notion, plus free text/Skip when supported. If the native tool is unavailable, ask the same choices in chat and wait. Do not make a fake in-report composer or create a ticket on initial click. Discover/connect the chosen provider and resolve its exact destination after the answer, preserving the finding and approvals.

Use **Save to ChatGPT Pages** and **Download Report** across skills. The former saves an editable snapshot to a private Page and returns its actual link; the latter returns a downloadable file. Do not call a file fallback a Pages save. Analytics additionally retain **Save as Live Site**. Neither Page saving nor downloading schedules a refresh. Preserve verified Noibu destinations using [console link guidance](console-urls.md). noibuLinks are navigation anchors, not follow-up actions; Open draft in Noibu requires successful creation/identity verification.

Read [action handling](presentation-actions.md). An action references a real report ID, workflow, domain, window, and target; verify these against conversation evidence or the handoff. Widget state is not a security boundary or guaranteed model memory. Do not rely on hidden saved state to recover a selected test or approved document.

Save as Live Site uses [the persistent dashboard workflow](connected-dashboard.md) and [permission preflight](site-permissions.md): build a private interactive Site containing the generated dashboard, retain current evidence in D1, verify totals and persistence, and publish it. The CTA's "Live" refers to the hosted URL, not a continuous data feed. Keep the adjacent freshness explanation. Offer weekly updates during setup, confirm day/time/timezone and notification intent, and verify the unattended source/writer before scheduling; declined or pending scheduling does not block publication. Never silently change security settings. Visitor-connected Noibu reads remain optional. Native scheduling uses the runtime guide and action handler, not browser cron, a Site's open-tab timer, or a Noibu backend scheduler.

For technical/fix actions across workflows, mark actual merchant/performance/accessibility findings with the appropriate category so Investigate routes to the shared GitHub handoff. Do not label a UX/operations finding technical merely to show a connection prompt. Get fix and draft-PR preparation use the same connection/repository check; vendor ownership stays a vendor handoff.
